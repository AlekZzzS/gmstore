## Запуск

### Docker

```bash
docker compose up --build
```

- витрина — http://localhost:3000/
- админка — http://localhost:3000/admin.html (токен `dev-admin-token`)

По умолчанию поднимается **4 воркера на одном порту** — так видно, что гарантии
однократной выдачи держатся на ограничениях SQLite, а не на однопоточности Node.
БД лежит в именованном томе `store-data` и переживает пересоздание контейнера.

Прогон всех проверок гонок в контейнере (поднимает свой сервер, своя БД, том не трогает):

```bash
docker compose run --rm tests
```

Настройки через переменные окружения:

```bash
PORT=8080 CLUSTER=2 ADMIN_TOKEN=secret docker compose up --build
```

Сбросить состояние вместе с томом:

```bash
docker compose down -v
```

### Без Docker

Нужен Node.js ≥ 22.5 (встроенный `node:sqlite`), `npm install` не требуется.

```bash
node server/index.js
```

- витрина — http://127.0.0.1:3000/
- статус заказа — `/order.html?id=ord_00001`
- админка — http://127.0.0.1:3000/admin.html (токен `dev-admin-token`)

Многопроцессный режим (4 воркера на одном порту) — так проверяется, что
гарантии не держатся на однопоточности Node:

```bash
CLUSTER=4 node server/index.js
```

Сброс состояния: `node scripts/reset.js`

## Как воспроизвести проверку гонок

Один командой — скрипт сам поднимает **отдельный сервер из 4 процессов** на
своей БД и своём порту, прогоняет все сценарии приёмки и убирает за собой:

```bash
node scripts/run-all.js
```

```
node scripts/run-all.js --workers 1     # то же самое в один процесс
node scripts/run-all.js --port 3300     # другой порт
```

Отдельные сценарии (нужен запущенный сервер на :3000):

| Команда | Что проверяет |
|---|---|
| `node scripts/race-buy.js` | 20 одновременных «Купить» с одним `Idempotency-Key` |
| `node scripts/race-webhooks.js` | 50 параллельных вебхуков, повтор `event_id`, вебхук раньше заказа |
| `node scripts/race-recovery.js` | пустой пул → восстановление → 10 параллельных повторных выдач; ловушка таймаута |
| `node scripts/race-promo.js` | лимит промокода под 40 параллельными запросами; расчёт скидки на сервере |
| `node scripts/stress.js` | 40 одновременных покупок при нестабильных поставщиках — глобальные инварианты |

## Как обеспечена однократная выдача

**Решение принимает БД, а не JavaScript.** Ни одна проверка вида
`if (order.status === 'paid')` не является основанием для действия — основанием
является либо `UPDATE … WHERE <ожидаемое состояние>` с `changes === 1`, либо
успешный `INSERT` в таблицу с `UNIQUE`. Проигравший гонку получает `changes = 0`
или `SQLITE_CONSTRAINT` и становится no-op. Все пишущие транзакции идут через
`BEGIN IMMEDIATE` в режиме WAL, поэтому гарантии держатся и между процессами,
а не только внутри одного event loop.

Четыре независимых рубежа:

1. **`webhook_events.event_id` (PK)** — повтор вебхука (at-least-once) физически
   не проходит дальше вставки.
2. **CAS-переход статуса заказа** — `UPDATE orders SET status='paid' WHERE id=? AND status='created'`.
   Среди 50 параллельных вебхуков с *разными* `event_id` переход выигрывает ровно один.
3. **`fulfillments.order_id` (PK) + `fulfillments.code` (UNIQUE)** — один факт
   выдачи на заказ и один код не более чем в один заказ.
4. **`provider_issues.request_id` (PK)** — «таймаут ≠ отказ»: повтор с тем же
   `request_id` возвращает тот же код и не трогает склад.

Плюс **аренда на выдачу** (`lease_owner` / `lease_until`): выдачу ведёт ровно
один исполнитель, а если процесс умер в середине — sweeper подхватит заказ после
протухания аренды. И **сверка прошлых попыток**: перед новой попыткой все старые
`request_id` переспрашиваются у поставщиков, иначе повторная выдача сожгла бы
второй ключ.

Подробности — в комментариях `server/core/fulfillment.js`.

## Что реализовано по этапам

### Этап 1 — витрина и базовый флоу

Верхняя часть витрины по макету: шапка, баннер, ряд иконок сервисов, блок
пополнения Steam, ряд карточек товара. Отзывы и футер по условию не верстались.

Флоу: «Купить» → `POST /api/orders` → страница статуса → «Оплатить (успех/неуспех)»
→ вебхук по контракту → автоматическая выдача ключа из пула → код на странице статуса.

### Этап 2 — однократная выдача под гонками

Двойной клик «Купить» гасится `Idempotency-Key` (PK в `order_idempotency`):
параллельные запросы с одним ключом создают один заказ, остальные читают
победителя. Вебхуки — рубежи 1 и 2 выше. Скрипты проверки — в таблице выше.

### Этап 3 — сбои и восстановление

Две заглушки-поставщика (A основной, B резервный) с настраиваемой долей 5xx,
таймаутов и задержек. Ключевое: заглушка **коммитит выданный код до того, как
«зависнуть»** — то есть таймаут действительно может означать «код уже выдан».

Статусы: `created → paid → delivering → delivered`, ветки
`payment_failed`, `out_of_stock`, `delivery_failed`. Два последних —
восстановимые, не падение.

В админке — список «оплачен, но не выдан» и кнопка безопасной ручной повторной
выдачи. Повтор идемпотентен: по уже выданному заказу возвращается тот же код и
не тратится ключ.

Дополнительно: код, выданный «зависшим» поставщиком и не доставшийся клиенту,
возвращается на склад (`POST /provider/:id/release`), поэтому на выданный заказ
расходуется ровно один ключ, даже когда заказ закрыл резервный поставщик.

### Этап 4 — промокоды

Лимит держится атомарным
`UPDATE promocodes SET used_count = used_count + 1 WHERE code = ? AND used_count < max_uses`
(+ `CHECK (used_count <= max_uses)` в схеме как последняя линия обороны).
Под 40 параллельными запросами `LIMIT3` применяется ровно 3 раза, `ONCEONLY` — ровно 1.

Скидку считает сервер по цене из каталога; от клиента приходит только строка
кода. Присланные клиентом `amount`/`discount` игнорируются, а вебхук с суммой,
не совпадающей с нашей, помечается `amount_mismatch` и заказ не оплачивает.

При неуспешной оплате бронь возвращается в лимит — ровно один раз, даже если
пришло пять параллельных вебхуков `failed`.

Бронь занимается при **создании** заказа — иначе лимит нельзя удержать под
параллельными запросами. Чтобы брошенный заказ не съедал место под лимитом
навсегда, неоплаченный заказ живёт `ORDER_TTL_MS` (по умолчанию 15 минут), после
чего sweeper закрывает его и возвращает бронь — как холд на билет. Возврат брони
и закрытие заказа идут одной транзакцией с CAS-переходом из `created`: иначе
поздний вебхук `paid` довёл бы заказ до выдачи уже после освобождения слота, и
скидку получили бы N+1 покупателей.

## API

### Витрина

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/catalog` | каталог товаров |
| `POST` | `/api/promo/preview` | предпросмотр скидки (ничего не резервирует) |
| `POST` | `/api/orders` | создать заказ, заголовок `Idempotency-Key` обязателен |
| `GET` | `/api/orders/:id` | статус заказа + история событий |
| `POST` | `/api/pay/simulate` | эмулятор платёжки: шлёт вебхук(и) на свой же эндпоинт |

### Вебхук оплаты

`POST /webhook/payment` — контракт из задания:

```json
{ "event_id": "evt_a1b2c3", "order_id": "ord_00123", "status": "paid",
  "amount": 500, "currency": "RUB", "created_at": "2025-01-01T12:00:00Z" }
```

Всегда быстрый `200` (выдача уходит в фон). Ответ содержит `outcome`:
`applied` · `duplicate` · `pending_order` · `amount_mismatch` · `ignored_terminal`.
Подпись не проверяется — по условию упрощено.

### Поставщики (заглушки)

`POST /provider/a/issue` · `POST /provider/b/issue` — контракт из задания.
`POST /provider/:id/release` — вернуть неиспользованный код на склад.

### Админка (заголовок `X-Admin-Token`)

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/admin/api/orders?filter=stuck` | «оплачен, но не выдан» |
| `POST` | `/admin/api/orders/:id/retry` | безопасная повторная выдача |
| `GET` | `/admin/api/stock` | остатки и текущие настройки сбоев |
| `POST` | `/admin/api/stock/topup` | пополнить пул |
| `POST` | `/admin/api/stock/drain` | опустошить пул (сценарий `out_of_stock`) |
| `POST` | `/admin/api/chaos` | доля ошибок / таймаутов / задержка |
| `GET` | `/admin/api/integrity` | сводка инвариантов для скриптов проверки |

## Структура

```
Dockerfile              рантайм-образ на node:22-alpine, без сборки
docker-compose.yml      сервис store + профиль tests
server/
  index.js              HTTP-сервер, режим кластера
  db.js                 схема SQLite — здесь живут все гарантии
  seed.js               данные из «Приложения. Материалы»
  routes.js             маршруты API, вебхука, поставщиков и админки
  http.js               мини-роутер и статика
  config.js             настройки через переменные окружения
  core/
    fulfillment.js      движок однократной выдачи (аренда, сверка, фиксация)
    orders.js           создание заказа, применение вебхуков
    providers.js        две заглушки-поставщика, ловушка таймаута
    providerClient.js   HTTP-клиент с таймаутом
    promo.js            промокоды с атомарным лимитом
    sweeper.js          фоновое восстановление
public/                 витрина, страница статуса, админка
scripts/                reset + четыре скрипта проверки гонок + run-all
```

## Настройки (переменные окружения)

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `PORT` / `HOST` | `3000` / `127.0.0.1` | адрес сервера |
| `CLUSTER` | `0` | число воркеров на одном порту |
| `DB_FILE` | `data/store.db` | файл SQLite |
| `ADMIN_TOKEN` | `dev-admin-token` | токен админки |
| `PROVIDER_TIMEOUT_MS` | `1500` | таймаут запроса к поставщику |
| `DELIVERY_LEASE_MS` | `15000` | срок аренды на выдачу |
| `AUTO_RETRY_STUCK` | `0` | фоновый автоповтор восстановимых заказов |
| `ORDER_TTL_MS` | `900000` | срок жизни неоплаченного заказа; по истечении бронь промокода возвращается в лимит (`0` — не истекает) |
| `SELF_URL` | по `HOST`/`PORT` | адрес для внутренних вызовов; при `HOST=0.0.0.0` подставляется `127.0.0.1` |
| `TEST_DB_DIR` | `data/` | куда `run-all.js` кладёт временную БД прогона |
| `PROVIDER_A_ERROR_RATE` и др. | см. `server/config.js` | стартовые доли сбоев |
